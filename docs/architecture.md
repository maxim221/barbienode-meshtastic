# Архитектура

## Плата

ESP32-S3 управляет SX1262-модулем E22-900M22S, хранит настройки Meshtastic в
NVS и раздаёт HTTP protobuf API. LittleFS содержит короткий кольцевой архив.
Система использует три проверяемых application-раздела:

- `app0`, адрес `0x10000`, размер `0x340000`: Meshtastic;
- `app2`, адрес `0x350000`, размер `0x300000`: MeshCore Companion BLE;
- `app1`, адрес `0x650000`, размер `0x300000`: RNode.

Адреса существующих `app0`, `app1`, NVS и LittleFS сохранены, поэтому переход
на triple-boot не требует их переноса. Один протокол активен в каждый момент.
Обработчики проверяют размер, SHA-256, формат ESP-приложения и отдельный маркер
проекта перед записью RNode или MeshCore. MeshCore подключается к сохранённому
домашнему Wi-Fi и на прежнем адресе показывает кнопку возврата в проверенный
Meshtastic `app0`; независимый резервный путь — команда `meshtastic` через BLE.
Удержание BOOT при запуске остаётся только физическим аварийным резервом и не
считается штатным способом переключения установленной на мачте ноды.

Свободный диапазон `0x950000..0xC8FFFF` выделен в отдельный `meshcorefs`.
MeshCore не монтирует LittleFS Meshtastic и при сбросе собственных данных не
стирает общий NVS с радиоконфигурацией и ключами Meshtastic.

## Orange Pi

Orange Pi — постоянный домашний сервер и единая точка входа для телефонного
веб-интерфейса. Пока нода находится дома, сервер обслуживает все три режима:
Meshtastic, RNode и MeshCore. Для MeshCore Orange Pi использует локальный
Wi-Fi/TCP Companion-сеанс и показывает каналы, контакты и локальный архив через
тот же веб-интерфейс. TCP принимает соединение только с фиксированного адреса
Orange Pi; собственного Bluetooth-модуля серверу для MeshCore не требуется.

BLE остаётся свободным для прямого подключения iPhone через нативное приложение
MeshCore и дома, и на выезде. Пассивный архив Orange Pi может работать
одновременно, но телефон и сервер не должны одновременно отправлять команды или
менять настройки: при активном управлении с телефона сервер переходит в
пассивный режим.

`web_server.py` раздаёт статические файлы и передаёт на плату только известные
пути API. Браузеру поэтому нужен один origin, а адрес платы хранится только в
конфигурации сервиса.

Когда плата работает в MeshCore, тот же веб-сервер показывает отдельный
мессенджер. `meshcore_bridge.py` держит TCP-сеанс с companion-прошивкой,
синхронизирует только включённые каналы и контакты и хранит локальный JSONL
архив с явной меткой `source=lora`. Его HTTP API слушает лишь loopback Orange
Pi; браузер обращается к нему через ограниченный `/meshcore/api/` proxy.
Сохранение мощности или координат не передаёт пакет. Сообщение и flood advert
уходят в эфир только после отдельного действия пользователя, а принятие
команды нодой не показывается как подтверждение получения адресатом.

Когда плата работает в RNode, официальный headless MeshChatX 4.9.3 на Orange Pi
единолично владеет `RNodeInterface`, постоянной LXMF identity, контактами,
историей и локальным propagation-хранилищем. Его защищённый Web UI доступен по
HTTPS на `:9337`; страница `:8082` оставляет управление радиопрофилем и
проверенный возврат по Wi-Fi в Meshtastic `app0`. Интернет-транспорт эта схема
не добавляет: в Reticulum настроен только локальный RNode через LoRa.

Propagation-хранилище, identity и очередь находятся на Orange Pi, а не в
прошивке ноды. При переходе в Meshtastic или MeshCore MeshChatX продолжает
работать, но `RNodeInterface` становится offline. После возврата в RNode он
подключается снова без пересоздания identity и потери сообщений. Автоанонсы,
автоповтор старых сообщений и периодическая радиосинхронизация выключены.

Для отладки тот же мост и веб-мессенджер могут временно запускаться
пользовательскими службами Linux-станции на `127.0.0.1:18766` и
`127.0.0.1:8083`, но постоянный домашний контур работает на Orange Pi по TCP.

Публичная история московского чата OneMesh загружается самим Orange Pi через
read-only API карты и возвращается браузеру тем же origin. Поэтому мобильному
браузеру в домашней сети не нужен прямой доступ к OneMesh или MQTT-брокеру.
Записи имеют отдельную метку `OneMesh API` и не считаются принятыми по LoRa.

`nightbot_archive.py` раз в минуту читает текущий и предыдущий JSONL-файлы,
дедуплицирует записи по SHA-256 нормализованного события и сохраняет их в
SQLite. Плата и веб-интерфейс работают, даже если архиватор недоступен.

## Сетевые режимы

1. В домашней сети плата подключается к Wi-Fi, Orange Pi — к плате.
2. После 60 секунд без домашней сети Meshtastic включает ранее настроенную
   защищённую AP `BarbieNode-Portable`.
3. После перезапуска снова первой пробуется домашняя сеть; fallback не меняет
   сохранённую клиентскую конфигурацию.

Интерфейс проверяет `/runtime-capabilities.json`. Ответ Orange Pi включает
серверные возможности; при прямом подключении плата возвращает статический
ресурс, и браузер выбирает автономный режим. В нём сообщения, запросы позиции и
трассировки передаются непосредственно через HTTP transport платы, а кэш нод,
координаты для локальных расчётов и замеры наведения сохраняются в браузере.
MQTT/OneMesh, суточная серверная история, автоматический Ping и память смены
профилей скрыты и не опрашиваются.

Роль ноды не связана с сетевым режимом: пользователь вручную выбирает `CLIENT`
или `CLIENT_MUTE`, поэтому кратковременная потеря Wi-Fi не меняет участие в
ретрансляции. Позиция телефона также не отслеживается: браузер выполняет один
запрос геолокации по кнопке и передаёт созданный `POSITION_APP` только после
второго явного подтверждения. При запрете геолокации или HTTP-ограничении
браузера координаты можно ввести вручную.
