# Сборка прошивки

Перед первой подачей питания соберите и проверьте аппаратную часть по
[подробной инструкции по распайке](wiring.md).

## Аппаратная схема

| E22-900M22S | ESP32-S3 GPIO |
| --- | ---: |
| BUSY | 4 |
| NRST | 5 |
| RXEN | 6 |
| TXEN | 7 |
| NSS / CS | 10 |
| MOSI | 11 |
| SCK | 12 |
| MISO | 13 |
| DIO1 | 14 |

Модуль объявлен как SX1262 с TCXO 1,8 В. Адресный RGB-светодиод находится на
GPIO48. Максимум target равен паспортным `22 dBm` E22-900M22S;
фактическое задание дополнительно ограничивает сохранённая LoRa-конфигурация.
Для этого target предел профиля RU также равен `22 dBm`; частотный план,
скважность, preset и слот не изменены. Образ установлен в `app0` по Wi-Fi через
RNode, сохранённое значение проверено повторным подключением: `22 dBm`.

## Воспроизводимая сборка

```bash
git clone --recursive https://github.com/meshtastic/firmware.git meshtastic-firmware
cd meshtastic-firmware
git checkout 608ff51c867da2004178f8c281397ffbc5079f6e
python3 /path/to/barbienode-meshtastic/firmware/apply-dualboot.py "$PWD"
pio run -e e22-s3-n16r8
```

Скрипт копирует overlay, добавляет HTTP endpoints и Wi-Fi fallback. Он
идемпотентен и останавливается, если ожидаемые anchors исходной версии не
совпали. Это намеренно: применять патч к другой версии без ревью опасно.

## MeshCore Companion BLE/TCP

MeshCore собирается из отдельного проверенного upstream checkout. Зафиксируйте
commit, примените локальный target и собирайте только application image:

```bash
git clone https://github.com/meshcore-dev/MeshCore.git MeshCore
cd MeshCore
git checkout a366955cb2f67b8e6842d4f00d2b6a554dddd88a
python3 /path/to/barbienode-meshtastic/meshcore/apply-meshcore.py "$PWD"
pio run -e BarbieNode_E22_S3_companion_radio_ble
```

Target использует ту же распайку E22, отдельные RXEN/TXEN, TCXO 1,8 В и предел
мощности `22 dBm`. MeshCore Companion сохраняет выбранную в приложении мощность
в диапазоне `-9..22 dBm`. Отдельный московский профиль MeshCore начинается с
868,731 МГц, BW 62,5 кГц, SF7, CR 7 и двухбайтового хэша пути в приложении;
перед будущей сборкой его нужно сверять с `https://meshcoretel.ru/ru`. Он не
изменяет защищённый профиль Meshtastic 869,075 МГц `MEDIUM_FAST`. Wi-Fi OTA намеренно выключен: в
triple-boot он мог бы выбрать чужой application slot. После запуска MeshCore
возвращается в сохранённую домашнюю Wi-Fi сеть и обслуживает на прежнем адресе
страницу с кнопкой «Вернуться в Meshtastic». Независимый возврат с телефона —
CLI-команда `meshtastic` по BLE в MeshCore Companion. Оба пути сначала проверяют
маркер Meshtastic в `app0`; физический BOOT остаётся только последним аварийным
резервом.

Для BarbieNode в MeshCore аппаратный CAD включён перед каждой передачей. При
занятом канале пакет остаётся в очереди, а проверка повторяется со случайной
задержкой; принудительная передача после штатного четырёхсекундного тайм-аута
upstream отключена. Это не подтверждение доставки: свободный канал означает
только возможность начать передачу.

Домашний Orange Pi подключается к Companion по TCP `192.168.1.31:5000`, а BLE
остаётся приложению iPhone. TCP регистрируется только через десять секунд после
старта BLE-контроллера: более ранний запуск Wi-Fi на ESP32-S3 вызывает гонку,
при которой недоступны и BLE, и веб-восстановление. Прошивка принимает TCP
только от фиксированного адреса Orange Pi `192.168.1.19`. Сборка с SHA-256
`4e8080752a27538826932e9642845c31ac5ab14eb84e2ce8af5ac683f421e3d5`
проверена 2 октября 2026 года: загрузка app2, TCP-мост, одновременная BLE-реклама,
удалённый restart и возврат веб-страницы после restart работают.

2 октября 2026 года после добавления mode-aware страницы Orange Pi повторно
проверен полный цикл `MeshCore → Meshtastic → RNode → Meshtastic → MeshCore`.
RNode определился через `/api/status`, отдельная страница открылась на основном
адресе Orange Pi, а её Wi-Fi-команда вернула проверенный Meshtastic `app0` без
физического доступа. После возврата профиль остался `RU` / `MEDIUM_FAST` /
slot `2`, `22 dBm`, `CLIENT`, transmit enabled; затем MeshCore снова загрузился
и TCP-мост переподключился. Во время приёмочного цикла пользовательские пакеты
LoRa не отправлялись. Без подключённого Reticulum-клиента RNode намеренно
оставляет радио неинициализированным, поэтому серверная часть Reticulum остаётся
отдельным этапом перед использованием этого режима.

Первая установка triple-boot выполняется по Wi-Fi только через специальные
маршруты этой сборки; стандартный Meshtastic OTA по-прежнему запрещён. Сначала
`GET /dualboot/partition-table` сохраняет исходный сектор `0x8000`, затем
`POST /dualboot/migrate/tripleboot` принимает только точную таблицу с ожидаемым
SHA-256, проверяет исходную dual-boot разметку и наличие RNode и записывает один
сектор штатным ESP-IDF partition-table OTA. Физические адреса NVS, LittleFS,
текущего Meshtastic и RNode не меняются.

Порядок первой установки, выполняемый только после отдельного подтверждения:

1. Экспортировать Meshtastic-конфигурацию без вывода ключей в терминал и скачать
   исходный сектор partition table; сохранить размеры и SHA-256.
2. Убедиться, что текущие application images меньше новых лимитов: `app0`
   `0x340000`, `app1` и `app2` по `0x300000`.
3. Обновить Meshtastic через точный RNode-маршрут
   `/api/update/meshtastic` (`meshtastic-app0`), не используя стандартный OTA.
4. Передать проверенный `partitions.bin` последовательными фрагментами и
   отдельной commit-командой в `/dualboot/migrate/tripleboot`; прочитать сектор
   обратно и перезагружать плату только после совпадения SHA-256.
5. Загрузить MeshCore через `/dualboot/update/meshcore` с целью
   `meshcore-app2`, SHA-256 и обязательным маркером образа. Meshtastic остаётся
   активным до отдельного переключения.
6. Проверить `RU` / `MEDIUM_FAST` / slot `2`, 869.075 МГц, 22 dBm, `CLIENT`,
   transmit enabled, MQTT policy и имена каналов без показа ключей. При ошибке
   остановиться и использовать сохранённый сектор для восстановления; NVS не
   восстанавливать поверх более новых данных без отдельного решения.

Для этой платы overlay также добавляет постоянный переключатель LBT через
`/radio/lbt`. По умолчанию он включён: перед передачей прошивка выполняет CAD и
при занятом канале откладывает пакет. Отключение пропускает только CAD;
случайная задержка конкуренции и остальные защитные проверки остаются.

Для target `e22-s3-n16r8` скрипт также разрешает точность MQTT Map Report
`16` бит вместо upstream-предела `15`. Это позволяет отображать намеренно
смещённую публичную точку BarbieNode внутри Гончаровского парка; обычные
LoRa-позиции и остальные targets не затрагиваются.

## Настраиваемые строки

Перед личной сборкой проверьте в `overlay/ReplyBotModule.cpp`:

- `PING_CHANNEL_NAME`;
- `PING_LOCATION`;
- тексты ответов и cooldown;
- `ENABLE_SCHEDULED_BEACON` — оставляйте `false`, если нет явной причины и
  согласования периодического трафика.

Пароли, channel PSK и координаты в исходный код добавлять не нужно.
